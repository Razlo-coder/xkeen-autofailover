# Разработка и проверка

## Сборка

Требуются Go 1.25+ (использовано 1.26.8), Node.js 22 и npm. Веб-интерфейс встраивается в Go-бинарник, поэтому сначала соберите его:

```sh
cd frontend
npm ci
npm run build
cd ..
go test ./...
go vet ./...
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -trimpath -ldflags='-s -w' -o build/xkeen-panel-aarch64 .
CGO_ENABLED=0 GOOS=linux GOARCH=arm GOARM=7 go build -trimpath -ldflags='-s -w' -o build/xkeen-panel-armv7 .
CGO_ENABLED=0 GOOS=linux GOARCH=mipsle GOMIPS=softfloat go build -trimpath -ldflags='-s -w' -o build/xkeen-panel-mipsel .
```

CI выполняет сборку интерфейса, Go-тесты, `go vet`, интеграционные проверки с Xray 26.9.9 и сборку трёх архитектур. Тег `v*` публикует бинарники, установщик, конфиг по умолчанию и SHA256SUMS.

## Состояние

`source_priority` хранится в `automation.json`: `all` (общий рейтинг), `first` или `second`. Он сравнивается перед страной и именем; при отказе или высокой задержке кандидата поиск продолжается в другой подписке. При включённом возврате переход к предпочитаемому сервису требует успешной проверки. Старые настройки без этого поля получают `all`.

`data/subscription.json` сохраняет прежние `url`, `last_updated` и массив серверов, добавляя `secondary_url`, `secondary_last_updated`, необязательные пользовательские имена `name`/`secondary_name`, полученные от провайдера `detected_name`/`secondary_detected_name` и `source_id` у каждого сервера. Старый файл читается как первая подписка. Обновление двух URL идёт параллельно; при частичном отказе сохраняется кэш не ответившего источника. Индексы пересчитываются в общем списке, а активный сервер и ручные страны связываются с источником и URI. Имена сервисов меняются отдельным защищённым API без обновления подписок. Ручное имя имеет приоритет; пустое ручное имя возвращает обнаруженное. Название `profile-title` читается из HTTP-заголовка или комментария в начале обычного/base64-содержимого, в plain UTF-8 или `base64:`; заголовок имеет приоритет. Неудачная загрузка не стирает прежнее имя.

Парсер распознаёт имена с явным суффиксом `· N` или `• N`, например `⚡ Авто · 1` и `🇫🇮 Финляндия+ · 1`, и добавляет `group_name`; старый кэш до вычисления этого поля дополняется при чтении. Одна карточка появляется при наличии хотя бы двух узлов с одинаковой основой имени в одной подписке. «Авто» и «Авто+» остаются разными группами. Ручной выбор группы пробует её разрешённые узлы параллельно и применяет самый быстрый подтверждённый. После отказа активного узла группы оставшиеся члены той же подписки ставятся перед общим списком кандидатов; возврат к более приоритетному серверу по пользовательским правилам остаётся отдельной проверкой. Объект балансировщика из JSON-конфига Happ не импортируется.

`data/automation.json` содержит пользовательские правила: enabled, country_priority, allow_other_countries, preferred_server_names, excluded_server_names, exclude_name_contains, quality_enabled, quality_threshold_ms, quality_fail_count, return_to_priority, priority_check_sec. Файл сохраняется атомарно с правами 0600. Если сохранить не удалось, действующие правила не меняются. Правила загружаются до фоновой работы. Старые JSON и YAML дополняются новыми значениями: контроль качества включён, 1500 мс, три проверки; возврат включён, 300 секунд. Явные false сохраняются. Старый UI может сохранить прежние поля без сброса новых настроек.

Параметры установки и служебная метка остаются в `config.yaml`; пользовательские предпочтения редактируются в UI. Старый YAML со списком стран без нового поля allow_other_countries сохраняет семантику строгого списка. При отсутствии automation.json используются старые правила YAML.

Идентичность проверяемого подключения определяется параметрами URI, а не отображаемым названием или индексом. Рейтинг и постоянные исключения задаются по названию, чтобы переживать ротацию адреса. Обновление, смена правил, ручной выбор и автоматическое применение сериализованы; кандидаты проверяются пулом до восьми тестовых ядер. Старый probe_concurrency может уменьшить параллельность, но значения выше восьми ограничиваются. VPNProber дополнительно ограничивает число дочерних процессов восемью.

Сетевые операции регистрируют отменяемый context. Ручное действие отменяет проверку списка, фоновый поиск, ручную пробу или загрузку подписки до ожидания operationMu; epoch отклоняет уже отменённые задания в очереди. Все дочерние процессы завершаются до освобождения блокировки. GET правил и списка не ждут operationMu. При отказе VPN автоматический выбор принимает первый результат сервера из заданных приоритетов до 400 мс по мере завершения проб, не ожидая другие, даже более приоритетные серверы; к ним можно вернуться обычным механизмом после восстановления. Если такой сервер не найден, применяется обычный порядок политики и порог качества. Пинг отправляет SSE по мере завершения проб. Перед применением кандидата оставшиеся пробы отменяются и дожидаются завершения; ApplyChecked остаётся единственной транзакцией записи и отката. Уже начатый restart/rollback не прерывается в середине. Остановка выключает watchdog до ожидания и вызывает диспетчер даже при ошибке сохранения automation.json. В режиме verified ручной restart дожидается окончания, чтобы последующая остановка не гонялась с асинхронным запуском.

`data/verified-current.json` атомарно сохраняет с правами 0600 имя, протокол, страну/ручную страну и SHA256 канонического outbound. URI, адрес и учётные данные подключения в этот файл не копируются. Имя восстанавливается только при совпадении отпечатка с фактическим `04_outbounds`; индекс подписки сам по себе не считается подтверждением. Канонизация совпадает с `SameOutbound`: исключаются tag/socket options, нормализуются существующие алиасы транспорта и пустой Reality spiderX. Ошибка записи оставляет имя в памяти и повторяет сохранение при следующем обновлении состояния. Повреждённые, слишком большие и несовпадающие записи игнорируются.

Задержка — минимум времени успешных HTTPS-запросов, каждый измеряется отдельно до чтения небольшого ответа. Неудачный запрос/таймаут не входит в это значение. Достаточно одного успеха для доступности; таким образом отказ одного сайта не провоцирует ротацию. Контроль качества не измеряет пропускную способность или потери пакетов. При высокой задержке `connected` остаётся true, но `quality_degraded` делает индикатор жёлтым.

Счётчики недоступности и высокой задержки независимы. Перед любым автоматическим поиском обновляется подписка. При отказе активного подключения сначала применяются доступные кандидаты в пределах порога качества. Если таких нет, серверы с подтверждённой доступностью и задержкой до 7999 мс используются как запасные; выбирается наименьшая задержка, а после перезапуска доступность проверяется снова. Когда текущее соединение доступно, другой медленный сервер не заменяет его. Ручной выбор медленного сервера запоминается в привязанной к отпечатку записи `verified-current.json`: качество отображается, но само по себе не отменяет намеренный выбор. Возврат к приоритету требует хорошей проверки нового кандидата. Неудачная проверка после перезапуска повторяется один раз, прежде чем `ApplyChecked` откатывает прежние байты.

`connection-session.json` содержит только время подтверждения, отпечаток outbound и идентификатор основного процесса Xray (загрузка системы, PID, время старта процесса). Его запись атомарна и закрыта правами 0600. Это сохраняет аптайм после перезапуска панели, но сбрасывает его при смене конфигурации, перезапуске Xray, обнаруженном отказе подключения или перезагрузке роутера. Тестовые процессы Xray в идентификатор не входят; данные подключения и URI в файл не копируются.

Возврат сравнивает строго более высокий рейтинг страны/имени, без перестановок по порядку подписки при равных рейтингах. Проверка ограничена интервалом и такой же паузой после любого выбора. Для сопоставленного ранее подключения сохраняется логическое имя/страна при обновлении IP и перезапуске панели; неизвестное подключение не получает предположительный рейтинг. Интервал и последнее переключение хранятся в памяти, после запуска выдерживается начальная пауза. Неудачные кандидаты используют прежнее временное исключение по URI, поэтому новый IP проверяется сразу.

## Интеграционные проверки

```sh
TEST_XRAY_BIN=/absolute/path/to/xray go test ./internal/xkeen -count=1 -v
```

Синтетические тесты не содержат пользовательских секретов. Включены проверки приоритета, исключения до проб, смены IP при прежнем названии, сохранения и миграции настроек, независимой задержки успешного HTTPS-ответа, трёх медленных проверок подряд, сброса счётчика, пропуска медленных замен, возврата по стране и имени, паузы после ручного выбора, отсутствия ротации равных рейтингов, отключения новых функций, неподменяемого HTTPS-пути через SOCKS, проверки с реальным Xray, отказа валидатора, отказа запуска, отката и восстановления прерванного переключения.

Опционально можно передать приватные пути `TEST_PRIVATE_SUBSCRIPTION` и `TEST_PRIVATE_OUTBOUNDS`. Файлы только читаются; конфиги разрешённых кандидатов проверяются локальным Xray без соединений с VPN-провайдером. Не добавляйте эти файлы в Git.

Параллельные проверки покрывают лимит восьми проб, отмену всех работников перед командой ядра, быстрые GET во время зависшей проверки, порядок приоритета при обратном порядке ответов, отмену старого списка перед загрузкой нового, отмену зависшей подписки и ручной пробы. Интеграционный тест запускает восемь реальных Xray одновременно и проверяет их остановку при отмене. Linux-тест API подтверждает вызов `-stop` даже при недоступном файле настроек. CI запускает весь набор с `-race`.

Проверки имени охватывают ротацию IP, перезапуск панели, ошибочный активный индекс, ручной выбор одинакового подключения с другим названием, откат, внешнее изменение конфигурации, повреждённую запись и повтор сохранения после ошибки диска. Для проверки интерфейса `TEST_UI_PREVIEW=1 go test ./internal/server -run TestAutomationAPIAuthPersistenceAndInvalidRules -count=1 -v` запускает на пять минут защищённую демонстрационную панель на `127.0.0.1:18080` с 70 синтетическими серверами первой подписки и группами «Авто» и «Финляндия+» второй. Режим предназначен только для локальной разработки: соединений с провайдером и переключений настоящего XKeen в нём нет.

Первоначальная версия ядра доработки проверена на Netcraze NC-3811, прошивке 5.1.6, XKeen 2.0 Stable и Xray 26.9.9: основной процесс работает, обе HTTPS-проверки успешны. Новые протоколы и UI проверяются отдельно локально/в CI. Сборка для архитектуры не является подтверждением работы на каждом устройстве: изменение режима перехвата или firewall требует проверки служебной метки и реальных соединений на целевом роутере.
